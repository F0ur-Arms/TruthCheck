TruthCheck v2

Progress report: multilingual healthcare misinformation verification
Branch v2-integration · first issued 16 October 2026 · updated 29 October 2026 · repository F0ur-Arms/TruthCheck

1. Summary (as of 30 October)

TruthCheck takes a health claim (English, Hinglish or Hindi) and returns a verdict, a confidence, a risk assessment and cited evidence. Over the last two weeks the work moved from "make the v2 pipeline real" to "measure it honestly and find where it fails".

  • The pipeline is real and runs end to end (sections 4 to 6): LangGraph orchestration over knowledge-base retrieval, reranking, an LLM evidence judge (Qwen2.5-7B, 64.7 to 65.4% vs 40 to 45% for dedicated NLI models), two-axis risk and a human-review pause.
  • The old evaluation set is broken (section 7). Its fake claims are short phrases and its real claims are long sentences, so style alone predicts the label. All earlier headline scores on it are confounded. A cleaner benchmark of 1,898 public-dataset claims replaces it for now.
  • On the clean benchmark the pipeline was biased to "false" (section 8): only 24% of true claims were called true, because passages on unrelated topics were judged as refutations.
  • A relevance gate and a stricter judge prompt remove the bias (section 9): balanced accuracy 0.598 → 0.706. The gate alone does this, so the more accurate prompt v1 is kept. The price is coverage: verdicts on 15% of claims, because for about 70% the knowledge base holds nothing relevant. Knowledge-base coverage is now the main limit.
  • Multilingual evaluation has started (section 10): on 413 English/Hinglish pairs judged against the same evidence, the judge changes its answer for about one claim in four when the claim is not in English (accuracy 62.0% English, 58.4% translated), and the pipeline's word-by-word normaliser makes it slightly worse (56.9%). The LLM decomposer now receives the original text instead (agreement with English 72.6% → 77.0%).
  • Clean end-to-end baseline (round 5, section 10): with all fixes together, balanced accuracy 0.726, verdicts on 16.6% of claims, 76.5% correct when answered.

2. The system

raw input
  -> normalisation / multilingual preprocessing         (src/preprocessor.py, multilingual/)
  -> claim routing + decomposition (LLM, heuristic fallback)   (src/claims_processor.py)
       medical-advice request  =>  NOT_A_FACT_CHECK
  -> per sub-claim: multi-lane queries, BM25 + dense retrieval, RRF, cross-encoder rerank
  -> per passage: NLI judgment + source tier + quality score   (src/evidence_engine.py)
  -> calibrated confidence and verdict                         (src/calibration.py)
  -> combine sub-claim verdicts                                (graph/nodes.py)
  -> two-axis risk (confidence vs. harm)                       (src/risk_engine_v2.py)
  -> high harm or medication-stopping claim: pause for a human (LangGraph interrupt)
  -> response with citations

Models. BAAI/bge-m3 (embeddings), BAAI/bge-reranker-v2-m3 (reranker), Qwen2.5-7B-Instruct-AWQ served by vLLM on the IIITD CB GPU cluster (claim decomposition and, now, the NLI judge). The old mDeBERTa NLI model remains as a fallback. Verdicts: SUPPORTED, SUPPORTED_WITH_CAVEATS, MIXED_EVIDENCE, MISLEADING, MOSTLY_FALSE, FALSE, INSUFFICIENT_EVIDENCE, NOT_A_FACT_CHECK.

Two entry points exist: the legacy main.py and the LangGraph app in graph/ served by app/api/main.py. They now share one evidence engine.

3. Where we started

The audit of the repository against the v2 redesign document found that the redesign document described more than the code did.

  • The LangGraph evidence node used a hardcoded NLI stub ("SUPPORTS" if "warm water" in text).
  • The human-review node approved everything automatically; confidence weights were hand-set; the harm score was not used.
  • The golden-set candidates were English-only and overlapped the evaluation set.
  • The reported baseline (accuracy 0.6831, F1 0.6709) was produced without the LLM connected and decided uncertain claims from a risk-score fallback.
  • The repository did not install cleanly (unresolvable spaCy model pin, Python 3.13 vs 3.11).

4. What was done

Step 0: Housekeeping

  • Made the repo installable on Python 3.11 (fixed the spaCy model pin, rewrote .gitignore, removed stray files).
  • Rewrote the README and removed config constants that nothing used.
  • Test suite brought to a passing state (now 86 tests).

Step 1: Honest evaluation

  • get_binary_prediction now returns Real, Fake, or abstain instead of silently falling back to a risk threshold.
  • New src/binary_scoring.py reports coverage, strict accuracy (abstain counts as wrong) and accuracy on answered claims.
  • generate_evaluation_report.py no longer invents numbers: it refuses to run without measured metrics.
  • run_validation_audit.py renamed smoke_audit.py because it is a smoke test, not an evaluation.

Step 2: Golden set (in progress, with the teammate)

  • Template and annotation guidelines written (evaluation/golden_set/GUIDELINES.md): 8 verdicts, language mix, population and cessation cases, double annotation with Cohen's kappa.
  • A validator (validate_golden.py) now checks the file against the guidelines. On the current file it reports: verdicts outside the taxonomy (TRUE/UNCERTAIN/PARTLY_TRUE), 100% English, no row labelled or annotated, no specific claim types, 33 duplicates, 1 overlap with the evaluation set.
  • About 2,260 rows have a claim, an evidence quote and a label, which is enough for the stage-level NLI test in step 4.

Step 3: Wire real components into the graph

  • Shared evidence engine (src/evidence_engine.py): retrieval, rerank, NLI, source tier and quality scoring in one class used by both main.py and the graph.
  • Graph nodes now retrieve from the 36,316-passage knowledge base for every sub-claim, run real NLI, and use source tiers read from the knowledge-base filename.
  • Risk: the two-axis risk engine is used. Only high harm or a medication-cessation override blocks a response for a human; low confidence is answered as INSUFFICIENT_EVIDENCE and flagged.
  • Human review: a real LangGraph interrupt(); the API returns pending_review and POST /api/v1/review/{id} resumes the same thread.
  • Persistence: SQLite checkpointer plus a SQLite store for review items and traces, so pending reviews survive a restart.

Step 4: Stage-level evaluation and fixes

  • Compared the graph with the legacy pipeline claim by claim. On simple claims they matched (coverage 0.28 vs 0.29, accuracy 0.90 vs 0.88), so the port was faithful. Multi-part claims were the problem.
  • Fix 1, sub-claim aggregation. Previously one noisy "false" sub-claim made the whole claim FALSE. Now supported plus refuted sub-claims give MIXED_EVIDENCE, and refutations only win when nothing is supported.
  • Fix 2, NLI judge. Isolated test of the NLI stage on 2,259 claim/evidence pairs (section 6). Replaced mDeBERTa with a Qwen judge, keeping a local NLI model as a fallback if the LLM server is unreachable.
  • Held-for-review claims are reported as their own category.

6. NLI stage test

To isolate the NLI stage, each model was given a claim and its gold evidence quote (2,259 rows from the public datasets in the candidate pool: ai4bharat, SciFact, HealthVer, COVID-Fact, PUBHEALTH) and asked for SUPPORTS, REFUTES or NEI. Majority-class guessing scores about 44%.

The dedicated NLI models are trained on short sentence pairs and struggle with abstract-length evidence. The Qwen judge's confidences are interim: each label's confidence is the precision it achieved on these rows (SUPPORTS 0.58, REFUTES 0.79, NEI 0.55) until a calibrator is fitted on the golden set.

7. Benchmark validity

A simple check: can the label be predicted from the claim text alone, without any evidence? If yes, a dataset rewards surface cues and pipeline scores on it say little about fact-checking. evaluation/artifact_check.py trains two text-only classifiers with 5-fold cross-validation: bag-of-words, and 10 style features (word count, length, digits, negation and hedge words, commas, final full stop, capitalisation, absolute words).

Cause. The run saved, for every claim, the passages used and the judge's label for each. Many correct "false" verdicts rested on equally weak evidence (median 0.25), so the 96% is largely the same bias.

9. Round 3: relevance gate and judge prompt

Relevance gate. Passages the reranker scores below 0.6 are dropped before judging; with nothing left the answer is INSUFFICIENT_EVIDENCE. The threshold was chosen on a random half of the claims and checked on the other half (simulation: balanced accuracy 0.596 → 0.712). Judge prompt v2. "Refutes" now requires a passage on the same subject that directly contradicts the claim; off-topic text is explicitly "not enough information".

The bias is gone, but for 1,293 of 1,854 claims no passage passes the gate. Prompt v2 also costs 6.7 points with correct evidence, so round 4 re-ran the gate with prompt v1. The gate alone is enough: balanced accuracy is the same (0.706 vs 0.704), but prompt v1 answers more claims (286 vs 232) with higher accuracy on them (72.4% vs 69.8%). It leans slightly back toward "false" (true claims called true 65% vs 74%), which is why the balance is unchanged. Prompt v1 with the gate is now the default; v2 remains available for use without the gate. Separately, 255 claims (13%) were held for human review: the keyword harm detector fires on topic words such as "cancer" or "COVID", which is too many for real reviewers.

10. Multilingual data and round 4

The teammate's branch golden-set-v1 (22 October, not merged) adds 1,050 rows: 700 Hinglish and 350 labelled Hindi. Validator findings: the "Hindi" rows contain no Devanagari (all romanized); the rows appear machine-translated from existing English claims, including some junk patterns; labels are still TRUE/FALSE/UNCERTAIN; no row is reviewed; translated rows skew false (571 vs 111 true). A copy of this report and ten chunk files were committed by mistake.

What it enables now: 413 translated rows pair one-to-one with an English original sharing the same evidence (278 Hinglish, 135 romanized Hindi). The running cross-lingual test judges the English claim, the translated claim, and the translated claim after the pipeline's own normaliser, against the same evidence, measuring accuracy and agreement with English. The normaliser matters: it maps word by word, e.g. "Kya aap apni neend mein seekh sakte hain?" becomes "kya aap apni neend in seekh sakte are?", and this is what the graph currently gives the judge.

About one judgment in four changes only because the claim is not in English. The most frequent change is the dangerous direction: 25 claims the judge refuted in English were judged "supports" in translation. The word-by-word normaliser does not help; it lowers both accuracy and agreement slightly. The translations are machine-made and the sample is small, so this is a first signal, but it supports translating claims properly into English before retrieval and judging.

Here each claim first goes through the LLM that splits it into English sub-claims; each sub-claim is judged against the same gold evidence and the results are combined with the graph's aggregation rule. The two translated rows differ only in what the decomposer receives: the normaliser's output (the current graph) or the claim as written.

No decomposition call fell back in this run (30-second timeout). Decomposition itself costs about 2 points against judging the whole claim directly (58.4%), and the gap to English (about 4 points, one judgment in four changed) remains: the next step is to test retrieval with the decomposer's English sub-claims, and to repeat this on real, reviewed Hinglish rather than machine translations.

11. Infrastructure and how to reproduce

  • LLM server: Qwen2.5-7B-Instruct-AWQ on vLLM 0.7.2, PBS queue Gpu1-10g (job limit one per queue, 48-hour walltime). Runbook: docs/LOCAL_LLM_DEPLOYMENT.md.
  • Evaluation jobs: scripts/cluster/eval_baseline.pbs, sharded across 4 to 6 processes on a 40 GB slice. The script picks the MIG slice for whichever queue it runs on and waits for the LLM server before starting. The cluster allows one running job per queue and two running jobs per user in total, so with the LLM server up only one evaluation job runs at a time; judge-only tests that need no GPU run on the master node in parallel.
  • Access: off campus the hostname does not resolve; the IP 192.168.3.91 works over the VPN.
  • The cluster account password is never stored in the repository.

12. Caveats and corrections

  • Correction to an earlier claim. During this work I said the LLM's own knowledge produced the baseline verdicts. That was wrong: verdicts come from the calibrator over retrieved evidence. The LLM affected only claim decomposition and legacy risk fields.
  • Style artifact (found 25 October). The 2,799-claim set can be classified at 98.7% from text style alone (section 7).
  • Partly contaminated run. In round 2's full-pipeline run, the first half of the shards started before the LLM server had loaded, so their first claims were judged by the local fallback model. The effect is probably small but cannot be counted. Jobs now wait for the server, and every claim records how many fallback judgments it used. Round 3 was unaffected.
  • Knowledge-base content. data/medical_kb/testing.txt holds 62 unsourced, hand-written statements, some matching old test claims word for word; it should probably leave the knowledge base.
  • Evaluation set limits. The 2,799 claims are sentences scraped from articles, not clean standalone facts, and they overlap the knowledge base. Real/Fake labels were assigned at sentence level. Treat scores as relative.
  • The legacy "fast path" (strong match to the 50 verified facts) always produced SUPPORTED evidence regardless of the NLI result and scored only 0.66, close to always guessing "Real". It was deliberately not ported to the graph.
  • Possible leakage. Some of the public datasets used for the NLI test may be in the training data of the models tested. The NLI comparison is a screening test.
  • Scoring choices. Held-for-review claims count as abstentions in the headline scores. Sub-claim aggregation and the NLI judge were chosen on these runs; both must be re-checked on the reviewed golden set.
  • Silent decomposition fallback. When the LLM call that splits a claim into sub-claims failed or exceeded a hard-coded 15-second timeout, the code quietly used a simple heuristic instead. Judging by the decomposition patterns, this happened for about 14% of claims in round 2 and 26% in round 3. The timeout is now configurable (30 s default) and every fallback is counted; rounds 2 to 4 ran with the old behaviour.
  • Interim parts. Calibration weights are hand-set; the judge's label confidences were measured with prompt v1; the harm score is keyword-based; the gate threshold was tuned on public claims, not on the target domain.
